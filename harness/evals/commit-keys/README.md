# commit-keys

Proves: the commit hook and acp check refuse every vendor-shaped key and key block in bin/sanitize's own list, and an AWS secret unless its value is a placeholder, so a key sanitize fails at a publish is refused at a commit, from an installed copy and from the plugin alike; the hook's own stricter shapes still block, while a publishable key, the docs' placeholders, ordinary .env.example, compose and shell defaults, a marked fixture line and a commit that takes a key out pass; every place a command could commit in is judged (the session's folder, every cd and pushd, git's -C, --git-dir and --work-tree, GIT_DIR and GIT_WORK_TREE however set, folders named inside quotes or through a simple assignment, a command passed to bash -c, every commit on every line), so subshells, conditions, pipes, here-documents and several commits in one command cannot move the judgment off a repository holding a key, and the report names that repository; cd - and popd, a commit message and an untellable folder on a git command that is not the commit do not refuse; a commit run through xargs, find -exec or submodule foreach, a folder that cannot be told, or more places than can be checked is refused; a key list that is missing, exits, does not parse or is empty refuses the commit and stops acp check, and so does a staged change or file list git cannot give or a check that runs out of time, which says so; a key is reported before any linter runs; a file that is not UTF-8, a name git has to quote or holding a space, and the user's diff settings neither refuse a clean commit nor hide a key; and a long line costs one pass, not one per character.
