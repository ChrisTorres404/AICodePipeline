# 1.4.1

## What changed

`wo close` no longer damages the knowledge base. Its grow step judged a profile by whether its
file name matched a feature the scaffold's own grouping found, and wrote `status: orphaned`
into every profile that did not match, whether the scaffold or a person had written it. Now a
profile is judged by the paths it covers: its SOURCE citations, read from the project root or
from the profile's own folder, and its Covers line, with wildcards expanded, backslashes read
as slashes, a leading `./` dropped and words that are not paths skipped. A profile that names
no path is checked through its feature key, mapped to a directory.

Grow, the step a close runs, adds a stub only for code no profile covers and changes no
existing profile. When a profile's covered paths are all gone it reports the profile and the
missing paths, and exits 3. `acp kb scaffold --grow --check` reports the same and writes
nothing. An explicit `acp kb scaffold` marks a profile orphaned only when the scaffold wrote it
and its covered paths are gone; a profile a person wrote is reported and left as it is.

The pipeline's own document folders (the folder holding the knowledge base, `WORKSPACE_DIR`
and `DOCS_DIR`) are never a feature, so a helper script kept with the documents no longer adds
a profile. A code folder that holds the knowledge base, such as `server/` for `server/docs/kb`,
still has its code profiled.

The close shows every line grow prints and keeps its errors. The closeout records the report
under its own heading, "Knowledge base changes at close", and records a failed grow step with
its output. Under the strict profile the close runs the report-only check first and refuses,
with nothing written, while a profile covers paths that are gone. `ACP_SKIP_KB=1` overrides it,
with a reason in the closeout, like the other refusals.

`acp doctor` and `bin/lint` read frontmatter with PyYAML when it is installed and with a
simpler rule when it is not. The simpler rule accepted a `key: value` line indented under a
plain value, which YAML rejects, so on a machine without PyYAML a skill with broken frontmatter
passed `acp doctor`. The rule now rejects it; none of the 550 shipped files with frontmatter
is affected.

## Where the changes came from

A project whose profiles were written by hand and split one source directory into packages
(`feature: engine-brain` for `engine/brain`, while the scaffold grouped all of `engine/` as one
feature) had 14 of its 15 profiles rewritten to `status: orphaned` at two closes, with "the
directory is gone" while every directory existed, and a `workspace.md` profile added because
helper scripts sat in its documents folder. The first fix was then reviewed by an agent that had
not written it. That review found that the new evaluation still passed with the path check
removed, that some citation and Covers spellings were reported as missing paths, and that a
knowledge base inside a code folder hid that folder's code. Those findings are fixed here.
The frontmatter fix came from the full evaluation run for this release: `baseline-and-doctor`
failed on a machine without PyYAML, in the unchanged 1.4.1 copy as well.

The evaluation `kb-close-keeps-profiles` now uses profile names the scaffold would never
produce, closes under the strict profile, and reads the closeout. The reviewer planted six
defects in copies of the code; each one makes the evaluation fail:

| Defect planted | Evaluation result | First check that fails |
|---|---|---|
| Path check removed (every covered path treated as missing) | FAIL | grow reports profiles whose paths all exist |
| Document-folder skip removed | FAIL | the knowledge base's own folder becomes a feature |
| Grow allowed to write `status: orphaned` | FAIL | grow no longer reports a moved scaffold profile (it rewrites it) |
| "Already covered" check removed | FAIL | grow adds a profile for code a profile already covers |
| Close output cut to its last line | FAIL | the close does not print the profile whose paths are gone |
| Strict refusal removed | FAIL | the strict profile closes with a profile whose paths are gone |

## Still open

- `acp kb scaffold --force` regenerates every profile, including one a person wrote with no
  `scaffold_prompts`. Its help text says so, and it predates 1.4.1; it is left as it is.
- A Covers item with a space in it is read as a word, not a path.
- With no `pipeline.config.sh` and no `WORKSPACE_DIR` set, a folder named `Workspace` at the
  root is taken to be the pipeline's documents folder and is not a feature.
